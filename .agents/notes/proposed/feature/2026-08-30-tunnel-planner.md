# 提案: 隧道规划器(可视化映射编辑 + 冲突检测 + 启动自检)

- Status: proposed
- Date: 2026-08-30

## 背景

现状: 拓扑散落在 config.json 的 remote_tunnels/forward_ports/local_ports/reverse_port
等字段里, 编辑靠设置页的表格式端口表(盲编), 场景模板只覆盖三种固定场景。痛点:
- 改端口/加映射时**冲突不可见**(本机端口已被占用、两条映射撞本机端口、与 dsh web
  端口撞车), 只有启动失败后才知道;
- 启动后"通没通"要自己开命令行探测;
- 愿景 §二.2 的"连线式规划、冲突检测、连通性自检、隧道组"均未落地。

基建已就绪: tunnel_mgr(Tunnel 引擎 + pid 持久化记录 sig/mode/forwards/watch)、
tcp_ok 探测、diagnostics.py(诊断报告)、monitor 体系。

## 方案(分两期)

### T1 单拓扑可视化编辑 + 校验 + 自检(本次提案范围)

1. **core/tunnel_planner.py(纯函数, 可单测)**:
   - `validate_plan(cfg) -> [问题]`: 规划内冲突——本机端口重复、-L 目标(主机:端口)
     重复、与 dash_port/lab_port/reverse_port 撞车、特权端口(<1024)警告、字段非法
     (端口范围/空目标);
   - `port_free(port) -> bool`: 新原语——实际 bind 一次本机端口测占用(tcp_ok 只测
     "有服务在听", bind 才能测"我能不能占用"; 两者结论互补);
   - 输出结构化问题列表(级别 error/warn + 中文文案 + 定位到哪条映射)。
2. **UI: 隧道页新增「规划器」面板(页面内分步, 不弹窗)**:
   - 映射表: [模式(-L/-R) | 本机端口 | 目标地址 | 目标端口 | watch] 行级增删改,
     数据源即现有 config 字段(单一代码事实源, 不另立文件);
   - [校验] → 问题清单内联展示; [应用] → 写回 config(save_config 自动 .bak) +
     热重载; [启动并自检] → 逐条映射启动后 tcp 探测本机端口, ✓/✗ 内联标注。
3. 自检/诊断复用 diagnostics.py 与 tunnels_snapshot, 不另造轮子。

### T2 隧道组 / 多套拓扑(独立候选, 对应 ROADMAP"多套拓扑切换")

- config 新增 `tunnel_plans: [{name, items}]`, 引擎按 plan 启停; 现有字段迁移为
  "默认 plan"(一次性迁移, 旧字段继续可读一个版本);
- 顶部部署选择器同款交互切换 plan; 批量启停/常驻编排在此之上。
- **默认不随 T1 一起做**, 见开放问题。

## 拒绝的替代方案

- **连线画布式 UI**: 视觉炫但实现重、表格+即时校验对小白更高效; 拓扑就 2-4 条边,
  画布收益为负。
- **让用户直接编辑 JSON**: 违背"小白用户"定位。
- **规划数据另立文件**: 与 config.json 双源必然漂移, T1 坚持单一代码事实源。

## 影响(若实施)

- core/tunnel_planner.py(新, 纯函数) + tunnel_mgr(port_free 原语) + 隧道页(规划面板)
  + 单测; 打包无需新增 hidden-import(静态导入)。
- 工作量估计: T1 约 1 个工作单元(与诊断报告相当), 风险低。
